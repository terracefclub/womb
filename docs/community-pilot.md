# Terrace private community pilot

Checked: 2026-10-28. Status: proposed technical decision, based on current primary sources; no deployment or runtime testing performed.

**Pilot HumHub Community Edition alongside the public Payload/SvelteKit website.** It matches the selected audience—current members and alumni—and the selected features: member profiles, stories, groups and opt-in mentorship. Keep community data and administration separate from the public CMS. Use existing software and configuration before developing social features in Payload.

## What the HumHub pilot includes

Use profiles with avatars, cover images, biography, cohort/year, interests and optional mentorship availability. Admin-defined custom profile fields and profile-wall posts are core features. This provides personal expression without developing a page builder. Arbitrary per-user scripts, HTML and full MySpace-style layouts are outside the pilot; use a shared accessible theme and revisit individual visual customization after people try it. [Core features](https://github.com/humhub/humhub/blob/master/README.md)

Create four initial spaces: Welcome, Terrace Stories, Mentorship, and a private Moderators space. Members can join additional interest or cohort spaces as demand appears. Here, “stories” means persistent text/photo posts with comments, not disappearing videos. Space membership and role permissions provide the boundaries; start with guest access disabled and profiles visible only to approved members. [Spaces and topics](https://docs.humhub.org/docs/about/humhub), [permissions](https://docs.humhub.org/docs/admin/permissions/), [guest/profile settings](https://docs.humhub.org/docs/user/user-management/)

**Mentorship needs configuration, not matching software.** Add optional “offering / seeking / both / paused” availability plus topics and a short introduction. Default to no participation. Use an opt-in Mentorship space and introduction posts so people can find one another, then contact each other directly. Do not copy private email addresses into a public directory or automatically enroll members. Search/filter behavior for the exact chosen fields must be verified in the pinned release; the space and its introduction posts remain usable without a custom search feature. A coordinator may make introductions manually. No scoring, recommendation algorithm or Windmill workflow is needed initially.

Install only the following additional modules, after resolving exact compatible release pins:

## Deployment boundary

Use a separate community hostname, application identity, database user and persistent volume. The planned Terrace identity provider can serve both systems through separate OIDC clients. Payload owns public newsletters, events and initiatives; HumHub owns profiles and private conversations. The public website links to the community. It does not read HumHub's database or index its content. Public republication of a member story requires an explicit editorial action and the author's agreement.

Keycloak admits only approved Terrace accounts to this client. An email domain or a successful Google login alone is not membership approval. Map the stable OIDC subject to the individual account, require verified email for account linking, and never map all members to one administrator. HumHub documents automatic linking to an existing account by email, making the verified-email requirement significant. Group-claim mapping and prompt removal of existing sessions after access revocation are not assumed to work automatically: test them and provide an idempotent disable/session-removal operation if necessary. [OIDC behavior](https://docs.humhub.org/docs/admin/oauth)

Package and bootstrap the service declaratively in Womb through the existing Nix/devenv workflow. Pin core, modules and image digests; build on falcon. HumHub's stock Docker workflow updates marketplace modules on startup, and migrations can make rollback require restoring data. A digest pin alone is therefore insufficient. Use an audited startup path with vendored, pinned modules and no marketplace updates, and prove a restart does not change versions. The exact supported mechanism still needs verification. [Module updates](https://docs.humhub.org/docs/admin/modules/), [migration behavior](https://docs.humhub.org/docs/admin/migrate-to-docker)

Run the application, MariaDB and required cron/queue processing; retain the default database-backed queue/search before adding Redis or a separate search engine. Monitor HTTP health, database connectivity, queue age, cron freshness, disk use and backup freshness. Private responses, media and API routes must bypass shared CDN caching. Keep Google Drive as the document system of record and link to its permission-protected files; no office server or file-sync service is needed. Keep Vaultwarden as a separate service, with its own credentials and data.

## Capacity and recovery

HumHub requires MariaDB/MySQL; it cannot simply share Payload's PostgreSQL database. Its stated 64 MB PHP allocation is not a whole-service RAM requirement. Uploads and backups add storage, and activity determines memory use. [System requirements](https://docs.humhub.org/docs/admin/requirements/)

**Planning estimate, not a benchmark:** reserve roughly 1–1.5 GiB additional RAM for a small HumHub/MariaDB pilot and test with 20–30 invited accounts and up to 10 active sessions. Start with photos/text, a 10 MB upload limit and a 5 GB media budget; use Drive for large documents and defer video hosting/calls. On a 4 GiB machine, Payload, PostgreSQL, identity, Vaultwarden, the OS and HumHub may leave inadequate headroom. Measure the actual combined stack before opening invitations; require at least 25% memory headroom and no OOM events under the pilot workload. An 8 GiB instance would be more comfortable if it fits the existing approximately $20/month total.

The proposal adds no paid application subscription. The server, provider backups, off-site storage, taxes and any transactional email costs must collectively remain within the approved budget. No new Hetzner quote or load benchmark was performed in this research. If measured capacity does not fit, keep the community preview on development infrastructure until on-premises capacity is available rather than silently increasing spend or removing backups.

Back up the database and uploaded files together, plus the configuration and release manifest needed for recovery. Encrypt the off-site copy, retain it independently of the VM, and rehearse a restore into an isolated instance. A per-user export is portability support, not disaster recovery. Proposed pilot targets are a maximum 24 hours of data loss and recovery within four hours, subject to the restore test. [Backup contents](https://docs.humhub.org/docs/admin/backup/)

## Acceptance and remaining decisions

Before admitting real members, test OIDC account linking, wrong/unapproved accounts, offboarding and existing-session termination; anonymous/private-space/media/API isolation; reports and moderator boundaries; complete user export; backup restore; restart reproducibility; and keyboard/mobile access to profiles, posting and messages. Exercise the public website during a community outage to prove they fail independently. Use synthetic accounts until these checks pass.

A synthetic-data preview is unblocked. Only two organizational inputs are necessary before real invitations: the authoritative current-member/alumni roster and who may approve access; and a named community moderator plus a backup who can handle reports and member removal. These do not require reopening the chosen audience or feature set. The proposed 20–30 person pilot and persistent-story interpretation can be changed after the preview without blocking its preparation.
